## 1. Что это

**Продуктовый прототип MVP:** React SPA + FastAPI. Инженер вводит **план/факт по неделям** → **Режим №1** → на Windows обновляется sample **`.mpp` через COM** → скачивание файла для MS Project.

Streamlit (`demo_app.py`) — оболочка с **тем же React UI** в iframe (отдельной Streamlit-формы нет).

Формулировка КП: *«веб-ввод данных → расчёт сроков начала/окончания в MS Project по фактическим данным → отображение»*.

| Контур | Смысл | Статус |
|--------|--------|--------|
| **A — BI-дашборд** | Сроки/отклонения в вебе | Прототип = блок Mode1 в SPA |
| **B — импорт в Project** | Исторически XML/CSV | Подтверждён ранее; **не основной путь UI** |
| **C — правка .mpp** | COM на Windows + Project | **Канонический выход текущего MVP** |

В SPA пользователю предлагается только **`.mpp`**. Сообщения про Mac/XML в UI не показываем.

## 3. Самостоятельный тест (чеклист)

### 3.1. Форма (текущий SPA)

1. Открыть http://localhost:5173 → префилл задачи **Ид 6 / Фундаменты сборные**.
2. Проверить месяц/год; план/факт; ВОР read-only из графика.
3. **«Сохранить и пересчитать»**.
4. Карточка Mode1: Начало/Окончание, остаток дней, факт периода, строка «было → стало».
5. **Windows + Project:** скачать `.mpp` → открыть в Project.
6. Без Project: тост/подпись «расчёт готов, `.mpp` недоступен на этой машине» — без обещания XML.

Полный сценарий показа: [`DEMO_SHOW.md`](DEMO_SHOW.md).

## 5. Выводы теста (25.07.2026)

1. **Парсинг PPT** через встроенный Excel (OLE) работает на тестовых слайдах (фундаменты + монолитная плита).
2. **Режим №1** даёт воспроизводимые даты при фиксированной «сегодня».
3. **Сопоставление** PPT↔задачи MSP по названию/объёму — OK на 2 работах.
4. **Импорт XML в Project** — файл открывается, структура задач на месте.
5. **Связи сохраняются**; при автоматическом планировании **каскад пересчитывается** (подтверждено: плита стартует через 13 раб. дней после окончания фундаментов).
6. После «голого» импорта даты могут сначала отличаться от демо, пока не зафиксированы ограничения/пересчёт; после установки окончания Id6 = 01.10.26 каскад сходится с ожиданием.
7. Прямая запись `.mpp` без Project **не требуется** для архитектуры B.

Старые формулировки «решение A/B не принято» и «ключевой тест импорта не завершён» — **снять**: тест B завершён положительно; A возможен как дополнение.

## 6. Рекомендации: архитектура A + C (MVP)

### Рекомендуемое решение для текущего демо

```text
Форма (SPA)
    → сервис расчёта (Mode1 + маппинг)
         ├─→ .mpp через COM (Windows + Project)   [= C, канон MVP]
         └─→ агрегаты / Mode1 в вебе              [= A, витрина]
```

- **Project** — рабочий график и каскад зависимостей (движок MS Project).
- **BI** — сроки, отклонения, % ВОР, прогноз дней, статус по объектам.
- Канонический обмен с Project в текущем MVP — **`.mpp` через COM** на Windows.
- Бинарный MPP не генерировать на Linux/Cloud без Project.

### Вариант «только A»

Возможен, если заказчик согласен, что «истина для отчётов» — BI, а Project обновляют вручную или реже. Минус: расхождение графиков без дисциплины обмена.

### Вариант «только B»

Возможен (уже доказан). Минус: нет единой веб-витрины для руководства без открытия Project.

## 7. Как довести демо до «идеала» (по приёмке XCA)

Цели теста: (1) перенос в ячейки, (2) пересчёт хвоста СМР, (3) связи не слетели.

| Слой | Идеальный путь | Не делать |
|------|----------------|-----------|
| Cloud / КП | Форма → Mode1 → отчёт в вебе; `.mpp` только с хоста Project | Обещать бинарный `.mpp` с Cloud |
| Локально + Project | Форма → COM → **`.mpp`** | Сравнивать «ДО» из чужого CSV с таблицей MPP |
| Каскад | COM → `Calculate` в Project | Ждать, что Mode1 у последователя останется 22.08, если связь `6ОН+13` тянет дальше |
| % / факт.даты | **Не писать** Actual* и % Complete | Старый COM с ActualStart (сбрасывал % 100→0) |

Уже в коде (`demo/mpp_writer.py`): только жёлтые поля (Text13–16, Number1/2, Start/Finish); `preserve_progress`; Number2 Mode1 после Calculate; проверка Pred/Succ в UI.

### Ближайший MVP (1–2 итерации)

1. ~~SPA + FastAPI + Mode1 + скачивание `.mpp`~~ — сделано (текущий контур).
2. Канонический выход UI: **`.mpp`** + строка было/стало + чеклист показа (`DEMO_SHOW.md`).
3. Жёсткий справочник работ (Id + нормативное имя) из БД вместо sample CSV.
4. Политика **Mode1 vs каскад**: для задач со связью FS — либо только ВОР+прогноз, либо даты + принять сдвиг Project.
5. Режимы 2–4 из ТЗ (среднее / веса / справочник) — следующий этап.
6. Многозадачная таблица «как Excel» из ТЗ — следующий этап.

### Интеграция с основным BI (`bi-analytics`)

1. После расчёта писать снимок в формат `msp_*.csv` → существующий ETL `web/` → `web_data.db`.
2. Экран: сроки СМР, отклонение от базы, «осталось дней (прогноз)», фильтр по проекту UUID.
3. Не читать PPT из дашборда напрямую — только результат расчёта из БД.

### Эксплуатация

1. Канал приёма данных (форма / БД / интеграции).
2. Версионирование: каждый прогон = timestamp + version_id (пока одна выгрузка job).
3. Аудит: кто запустил, какие Id изменились.
4. На Cloud — демо без секретов; боевой `.mpp` — только хост с MS Project.

### Не делать

- Писать `.mpp` на Streamlit/Cloud без Project.
- Обещать в UI Mac/XML как основной путь текущего MVP.
- Переписывать движок связей Project в Python «на всякий случай».
- Смешивать клиентский `web/` основного дашборда с демо-фикстурами.

## 8. Ответ для КП / протокола

> Текущий MVP-выход: **C (правка .mpp через COM)** + веб-витрина Mode1 (**A**).  
> A — BI/веб по срокам и отклонениям (прототип: React SPA + FastAPI).  
> C — скачивание обновлённого **`.mpp`** на Windows + MS Project.  
> Исторический контур B (импорт XML) подтверждён тестом 25.07.2026, но **не является основным UI-путём** текущего демо.  
> Без Microsoft Project бинарный `.mpp` не формируется.
